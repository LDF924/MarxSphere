# 写作舱 · 研究证据链(假设 → 检验 → 发现 → 正文)

> 2026-09-25。这一批补的是写作舱**最根本的一条断线**: 正文里没有任何研究证据。

## 为什么要做

真实科研的顺序是 **先有数据与发现, 再写正文**。而改之前, 写作舱的章节生成器
`generateChapter()` 拿到的上下文只有这些:

```
论文主题 / 核心论点 / 本章标题 / 全文大纲 / 前文摘要 / 语体 / 可引文献池 / 参考样例
```

**没有任何位置放"数据、结果、发现"**。三处实测(grep 核过, 不是推测):

| # | 现象 | 证据 |
|---|---|---|
| ① | 生成 prompt 里没有研究证据的位置 | `paper-outline-service.ts` 的 `generateChapter` 参数表 |
| ② | 后端**早就写好**了一条素材注入通道, 但它是**死代码** | `research-exec-engine.runLlmJob` 里的 `【可用素材】` 只在 `chapter_gen\|finalize\|writing` 下触发, 而那是 `executorMap` **未命中**时的兜底分支。写作舱用的 jobKind 全部命中 executorMap, 且那三种 jobKind **全仓无人创建** ⇒ 这条通道一次都没执行过 |
| ③ | 假设只躺在 analysis 节点的 JSON 里 | 没有"检验结论"这个字段, 也不进任何 prompt |

后果: 跑完回归、选好素材, 生成出来的正文与它们**毫无关系**。用户只能手动把系数抄进正文,
而抄错没有任何信号。

## 做了什么

### A 批 —— 研究者带证据进来

| 能力 | 位置 | 说明 |
|---|---|---|
| **本章依据** | 创作台正文上方 | 每章勾选依据(素材 / 分析结果 / 假设 / 发现), 可写"本章用它做什么"。生成时组装成证据块注入 |
| **证据块预览** | 同上 | 显示"生成时到底给模型看了什么" —— 不做黑箱 |
| **假设检验台账** | 资料页「研究台账」 | H1..Hn + 结论(支持/部分支持/否定/待检验) + 依据(哪个回归的哪个系数) |
| **正文数字核验** | 创作台正文下方 | 正文里的数字必须能在本章依据里找到; 对不上就标出来 |
| **研究设计落库** | 框架设计页 | 方法/识别策略/数据来源/伦理 落 `design` 节点, 并作为**全文约束**注入生成 |
| **变量可编辑** | 框架设计页 | 此前是只读卡片(LLM 抽错也改不了) |

### B 批 —— 系统产生发现

| 能力 | 说明 |
|---|---|
| **自动采集** | 统计分析**跑完即**把系数表抽进台账(不需要人点)。挂在任务完成处而非 API 层 —— 三条建 job 的路径自动全覆盖 |
| **代码写数字** | 抽取按**表头精确匹配**, 不让 LLM 读数字。截距排除; 抽不到的行会报出原因 |
| **结果段生成** | 从台账生成「结果」章: **数字先由代码写成句子骨架**, 模型只负责连缀成段 |
| **假设匹配建议** | 按变量名/系数在假设文本与依据里的出现匹配, 摆出"看起来相关的那几条"。**只提议不判定** |

## 关键设计取舍(为什么这么做)

### 1 数字绝不让模型复述

`research_findings` 的每一列(系数/标准误/t/p/CI/N/R²/星号)都是从 `stats_jobs.result`
的表格里按列名精确抽取的。模型只负责写那句自然语言(`claim`)。

理由: 如果数字是模型写进 prompt 的, 那"数字核验"就变成了"核对模型与自己", 恒真 —— 毫无价值。

### 2 核验只报告, 不改写

系统能证明"这个数不在你的结果里", 但**不能替研究者决定改成什么**:

- 也许它来自另一次没选进本章依据的分析 → 那是"依据没选全";
- 也许是从别的文献引的 → 那就该标出处;
- 自动"修正"成最接近的系数是**最糟**的做法 —— 那会把一句标了出处的引文变成假数据。

### 3 精度下界是 1 位小数

`roundTierMatch` 的判断是「**写出来的数本身就是依据某个精度的正确四舍五入**」,
而不是「两者在某个精度下相等」。从 1 位小数起(不是 0 位)。

> 这里写错过一次: 第一版从 `d=0` 起, 于是 `round(0.312,0)=0` 与 `round(0.35,0)=0` 相等
> ⇒ 0.35 被判"对上了 0.312"。**这是把错的判成对的**, 而整条核验链的价值全在"抓错"上。
> 单测里有一条专门钉住它。

### 4 发现不能手填

`research_findings` 表**没有**"新建"入口。没有溯源列的"发现"就是编的, 而编出来的数字
一旦进了正文, 整篇论文的可信度就没了。手写的结论请放假设台账的「依据」栏 ——
那里是研究者自己的话, 性质不同。

### 5 归属按数据文件, 不按项目

统计结果按 `user_id` 存在 `stats_jobs`, 与写作舱的 `research_projects` **没有任何一列相连**。
唯一的连接点是本课题第 3 步上传的数据文件(快照里的 `statisticsFileId`)。
所以 `autoHarvestForFile` 按它反查**所有**关联课题, 各存一份; **没有数据文件的分析不采集**
(不该凭空归到某个课题)。索引见迁移 153。

## 数据模型

迁移 `154_research_evidence.sql`, 三张表:

- `research_chapter_evidence` —— 章节依据(`kind` 四类 + 软引用 `ref_id` + `note`)
- `research_hypotheses` —— 假设台账(四态结论 + 依据 + 说明)
- `research_findings` —— 发现台账(溯源列齐全 + `claim` 一句话 + 三态采纳状态)

依据的 `ref_id` 是**无外键的软引用**(按 kind 指向三张不同的表)。加外键就要拆表或拆列,
而查询侧永远是"按章节一次取全部依据"。代价是被引用对象删除后会悬空 ——
读取侧逐类过滤并丢弃取不到的, 计进 `dropped`, 不报错也不显示空壳条目。

## 实证台(因果推断)与统计台的关系

写作舱的证据有两个来源, 走**两条不同的路**:

| 来源 | 数据在哪 | 怎么连 | 覆盖什么方法 |
|---|---|---|---|
| 统计台 | `stats_jobs` | 按**数据文件 id**(`workbench_snapshot.statisticsFileId` ↔ `stats_jobs.input->>'fileId'`), 迁移 153 建了索引 | 17 法(描述/回归/相关/信效度…) |
| 实证台 | `empirical_pipeline_runs` | 按**显式绑定**的 `research_projects.empirical_project_id`(迁移 155) | 19 法(含 DiD / IV / RDD / PSM / 合成控制 / 事件研究) |

两条都要, 因为**它们互不覆盖**: 实证台的因果识别方法根本不走 `stats_jobs`, 而统计台的
17 法也不写 `empirical_pipeline_runs`。合并成一条会丢掉一半方法。

### ⚠ 实证台这条线的安全模型(必读)

`empirical_projects` **没有 user_id 列**, 实证台的 63 个路由**没有一处调 `requireUser`**,
服务端对本机连接全豁免 —— **实证台的数据本来就是"实例级"的, 没有用户隔离**。

本功能**不假装**补上了隔离(那需要加列 + 回填 + 改三个创建路径, 是另一件事)。
它做的是: 绑定由用户**显式设定**、运行时校验课题存在、只按设定的那**一个** id 读、
不提供"列出全部实证数据"的接口 —— 越权面与实证台自身一致, 不扩大。
**界面上如实写明了这一点**(见 `ChapterEvidencePanel` 的警示条), 否则用户会误以为
"写作舱里看得见"等于"这是我的私有数据"。

## 踩过的坑(改这块之前值得读)

### 1 两套表结构键名不同, 导致实证台结果一条都抽不出来

`statistics_runner.py` 输出 `{title, columns, rows}`, `empirical_runner.py` 输出
`{title, cols, rows, notes}` —— 而读取侧只认 `columns`。修法是 `tableColumns()` 归一化。

### 2 抽取器按**名字**判, 而实证台的表叫别的名字

原先写死 `回归结果|ANOVA` 这个标题正则, 列名写死「标准误」「p值」。实证台的表叫
「OLS 回归」「期间」「路径」「条件」, 列叫「SE」「p」—— **全部落进 skipped**,
而界面只说"没有可抽取的系数表"。现在改成**按结构判**(有「变量」类列 + 有「系数」列),
并且: 标题看着是系数表却抽不出来时**必须报出原因**(含实际列名), 不许静默跳过。

### 3 `empirical_pipeline_runs` 曾要等森林图才写

原实现先 spawn 一次 Python 画森林图(轮询最长 ~33 秒)**之后**才写管道记录。
后果: 一次成功的回归要等几十秒才在流水线里出现; 某些失败路径会 `return` 掉整条写入;
服务在这几十秒内重启 → **记录永久丢失**。改成结果一到就写, 图算完再补一遍(同 `runTaskId` 更新)。

### 4 写路径"发出去就不管"会让下游读到旧状态

`statistics-job-service` 完成任务时原先 `void persistJob(job)`, 而紧接着的自动采集
**要从库里读** `status='completed'` 那一行 —— 并发时读早了就采到 0 条, 表现为**偶发**失败。
改成 `await`(那个回调也随之改成 `async`; 第一版只加了 `await` 没改 `async`,
esbuild 转换失败导致**所有统计任务 500**, 而 `tsc --noEmit` 抓不到 —— 必须真跑一次)。

### 5 绑定之后才回补 —— 顺序反了就是空台账

自动采集挂在"运行落库那一刻"。那一刻如果**还没绑定**, 就没有任何课题可写 ——
那批结果**永远不会**进台账。而"先跑分析、后建写作课题"恰恰是最自然的顺序
(实证台本来就先于写作舱用)。
**这是探针逼出来的**: 它的顺序正好是"先跑 OLS、后绑定", 结果红了;
修法是 `bindEmpiricalProject` 在绑定时**回补**该课题下最近 20 条带表格的运行。
探针里那条断言("绑定前的既有运行被回补进台账")就是钉住它。

## 用户级隔离(做到哪一步)

迁移 156 给 `empirical_projects` 加了 `user_id`, 配套改动是**向后兼容**的:

| | 行为 |
|---|---|
| 新建课题 | 记录归属(有 token 就写, 没有写 null) |
| 历史课题 | 一律 `user_id = null`, 界面标「⚠ 历史未归属」 |
| 列表 | 有归属的只对本人可见; 未归属的仍对所有人可见 |
| 绑定/读取 | 归属别人的**拒绝**; 未归属的放行 |

**没有回填历史归属, 是刻意的**: 试过两个来源都不可靠 ——
`empirical_results` **没有 project_id 列**(只有 file_id), 且它的 user_id 是迁移 127 才加的、
历史行恒为 null; `empirical_pipeline_runs` 也没有任何用户列。
**猜错的归属比没有归属更糟** —— 那会把别人的课题锁死在错误账号下, 而且没有任何界面能让人发现。

**仍未做**: 实证台其余 60 个路由**尚未**做归属校验 —— 它们仍然对本机访问全开放。
本列是收紧的第一步, 不是完整隔离。这一点在迁移注释与界面警示里都写明了, 不含糊过去。

## 双向反跳

| 方向 | 通道 | 说明 |
|---|---|---|
| 写作舱 → 实证台 | `setEmpiricalTarget` 写 localStorage → 跳转 → 实证台挂载时 `takeEmpiricalTarget()` | 带着**当前绑定的课题**过去, 不用在下拉里重新找。读后即删 |
| 实证台 → 写作舱 | **不需要按钮** | 运行落库即自动入台账(与统计台对称), 写作舱那边直接就能勾选 |

⚠ 走 localStorage 而不是 postMessage: 目标视图可能**还没挂载**, 那时没有监听器, 消息会静默丢
(同 `writePendingRoute` 踩过的坑)。两个 key 的字符串在两侧各导出一次(`__EMP_TARGET_KEY`)便于对照。
